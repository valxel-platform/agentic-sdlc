Valxel SDLC Architecture

One service that takes a feature from idea to production and keeps it healthy there. Agents do the work, people decide at gates, and every product's own governance repo sets the rules the tool must follow.

How work moves through it

Idea to production

One feature thread, across every repo it touches.

  1. The intake agent drafts the intent with the person and checks what the product already has.
  2. Discovery, then spec, approved at G1 and G2.
  3. Design and architecture run in parallel, approved at G3 and G4, then join. The architect's diagram is published to Lucid or draw.io for G4 reviewers.
  4. New repos are provisioned from templates; the planner splits the work; one coder agent per task, one reviewer per PR.
  5. CI must go green. High-risk and regulated changes need G5. The merge train merges libraries, then providers, then consumers.
  6. OpenChoreo builds the merge commits and deploys to dev, then staging.
  7. Release managers approve production and a rollout plan at G6.
  8. The flag steps through 5, 25, 50 and 100%, holding on nearby incidents and stopping if users with it on fail more.

Signal to resolution

The tool does the heavy lifting; on-call is paged only when it can't.

  1. A signal joins an open incident or opens one. A SEV1 sends on-call a low-urgency heads-up.
  2. OpenChoreo's root-cause agent investigates, on a provider allowed for the data class, while the tool correlates recent changes.
  3. Triage proposes actions. Suspects are recent releases and features still rolling out nearby.
  4. When the policy allows and the analysis agrees, the tool turns the flag off or rolls back, and records the change.
  5. It watches for recovery. If it can't act, its action fails, or the failure continues, it pages on-call urgently.
  6. The fix goes back through the pipeline as a hotfix; the postmortem is drafted into the governance repo.

What every step leaves behind

For audit, and for looking back at what went wrong and what it cost.

  • Each decision: who approved, at which gate, with how many active minutes.
  • Each production change: who or what made it and why, with a ServiceNow receipt.
  • Each model call: role, model, tokens, cache hits and cost, in the usage ledger.
  • Each feature's cost in production, from FinOps, beside its build cost.
  • The resource inventory: what runs in production against the lower lanes, with cluster identifiers.
  • Traces of every thread, and postmortems and ADRs in Git.

Design rules

Agents work, people decide

Seven gates (G0 to G6) are interrupts that wait for an approver from the product's own governance repo. Three failed evaluator loops, or a spent budget, hand the phase to a person.

Products own their rules

The tool keeps no product settings. It reads each product's governance repo and pins it by commit for the life of a feature. Products can tighten the platform's rules, never loosen them.

Data class picks the model

The gateway only routes PHI and payments work to providers covered for it. The same rule decides which provider OpenChoreo's root-cause agent may use.

Production stays human, with two exceptions

Promotion to production is a person's decision at G6. The tool may act on its own in only two ways: turn off a recent feature's flag, or roll back a recent release, and only when the policy allows it and the analysis agrees.

Threads survive anything

LangGraph checkpoints every step in Postgres. Waits on people, CI and deploys are resumable after a restart, and one replica serves live updates.

Every integration is an interface

Stub mode runs offline and deterministically; live mode swaps in Claude Code, the Claude API and the real systems one interface at a time.
